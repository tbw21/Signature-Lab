# Consolidated Signature Lab: physical-device acceptance

**Status: checklist supplied; actual acceptance not completed here.** Use the exact
frozen candidate and record failures, unavailable checks and refused transactions.
A blocker disqualifies those bytes; fixes require a new candidate and full restart.
No physical result may be replaced with an expected signature generated by the Lab.

## Record before starting

Record the HTML and source ZIP SHA-256, authenticated publisher-key fingerprint and
verification result (or explicitly unsigned), operator/date, signer model and hardware
revision, actual firmware version and how its authenticity was checked, host/phone OS,
browser version, opening mode/origin, QR format and disposable-wallet word length.
Do not claim an operator-entered label or matching wallet fingerprint attests device origin.

Start with one supported SeedSigner configuration that the operator actually has.
Do not claim other devices or firmware releases are compatible from its results.
Use a spare device or a supported temporary-wallet procedure. Never overwrite a real
wallet, enter real wallet words, fund test addresses or weaken a signing safeguard.

## Establish the individual physical workflow

1. Open the exact saved file and separately the intended secure website deployment,
   without test shims. Test each browser/OS combination intended for support. Record
   any camera-origin restrictions, file import/export behavior and absence of test-data
   network requests. Do not bypass browser administrator policy.
2. Create fresh 12-word and 24-word disposable wallets, scan the real SeedQR and compare
   device words/fingerprint. Verify leading-zero fingerprints when a disposable test
   vector is deliberately used; never fund that public vector. New wallet updates the
   display; same-wallet transactions retain it; unavailable QR/root state does not show
   an old fingerprint.
3. Manually review and sign the displayed native SegWit transaction on the actual device.
   Compare recipient amounts, addresses, change and absolute fee in matching units.
   Return a signed response. Save the original response and current-result evidence.
4. Exercise BC-UR and BBQr where that firmware actually supports them; record unsupported
   formats rather than claiming a failure of cryptography. Exercise PSBT v0/v2/raw returns
   where available, long/many-input transactions and the six scenario families. A device
   refusal of invented/boundary data is an uncompleted case, not proof of malware.

## Compare individual and guided behavior

Use a disposable wallet and the exact same unsigned transaction on both paths, with the
same explicit method policy and state. Have the physical device produce each response;
do not substitute browser-generated references. Inspect signed bytes and metadata under
both paths. Document real differences and legitimate transformations, not just green text.
The browser cannot itself attest that a duplicate was freshly signed.

Before the first attempted signature, plan a short 3-6 case session, then qualify the
intended longer count with actual device operations. Verify fixed wallet/policy/format,
case number and plan identity; review and approve EVERY transaction on the signer.
Next and camera Start must require operator action. No seed reload should be needed for
ordinary same-wallet continuation. Check new-wallet/editor controls remain locked.

Return a deliberately wrong case, incomplete response, harmless unexpected metadata and
an independently reviewed differing-signature fixture. Each must remain a visible finding
and halt guided advancement. No queued file result, repeated click or camera callback may
skip a case, duplicate progress or revive a stopped run. Record a genuine signer refusal
through End session. End must preserve findings, stop page capture and allow manual work
without pretending a device operation was undone.

## Optical and lifecycle faults

Measure scan acquisition and completion under usable brightness, glare, distance, camera
focus, rotation, dense/long QR sequences and ordinary lighting. This release does not claim
new speed/density settings or an optical improvement. Keep the physical device's review.

Test unanswered permission beyond 30 seconds, late permission after Stop/expiry, delayed
video startup, repeated Start, ended/disconnected track, revoked permission, stalled video,
screen lock and background/return. Verify released capture resources, explicit terminal
messages, no automatic reacquisition and preserved guided halt. Pause/cancellation is not
a permission to silently repeat a signing operation whose outcome is uncertain.

## Evidence, recovery and user understanding

Save current-result evidence BEFORE advancing when raw responses are needed. Save session
report and independently inspect its plan hash, requested/completed/not-completed counts,
per-case outcomes, metadata warnings, capture/incomplete findings and End reason. The
session report is a compact public summary, not a complete original-response replay bundle.
Run the independent public replay utility on each saved per-result evidence file using a
trusted separate environment. It checks consistency, not publisher/device authenticity.

Reload/crash must start fresh; no persistent seed or crash-resume is expected. Back/Forward
restoration may retain memory but must not start camera or advance. New wallet resets the
run; save first. Test download/full-disk/read-only and actual host/device interruption safely,
recording actual OS faults separately from injections. For rollback, close the candidate and use only a separately approved previous version with
its recorded hash and a fresh test. If no acceptable fallback exists, withdraw the affected
candidate rather than selecting an older version by name. Never change frozen candidate bytes.

Ask nontechnical users what a match, difference, incomplete response, unexpected metadata
and completed session mean. If they infer firmware certification or a safety percentage,
revise the design in a new candidate. Do not substitute an extra disclaimer for observation.

## Measure time without removing review

Record time spent on page navigation/setup, outgoing QR acquisition, on-device review and
approval, response capture, verification and saving. Compare the same device/conditions and
case set between individual and guided workflows. Identify avoidable page work separately
from necessary device approval. No time-saving claim is warranted before this measurement.

## Acceptance record template

For each case record: ID, requirement, exact setup, procedure, expected behavior, observed
behavior, passed/failed/skipped/unavailable, original-response/evidence filenames and hashes,
operator/date, refusal/cancellation reason and limitations. Counts of simulated/software
cases must never be added to physical operations. Close provenance, publisher and independent
review gates separately before broader promotion. Matching signatures cannot prove future
firmware behavior or rule out all hidden information.
