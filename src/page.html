What does a guided physical-device session do?
Back to contents

A session fixes 1–200 public test transactions before signing begins, using the same disposable wallet and selected policy. The six existing scenario types are balanced across the plan. Planned scenarios are not recorded as completed coverage until their returned signatures are checked.

The actual signing device still receives, reviews and signs each transaction. This page does not upload firmware, run a simulator, press device buttons, sign on behalf of the device or start its camera automatically. Every response goes through the same verifier as an individual check.

A signature difference, unexpected metadata, incomplete import or camera failure stops advancement. There is no automatic retry or silent skip. Save relevant evidence and end the session explicitly before investigating with individual tests. The session report retains the earlier finding; a later match does not erase it. A device refusal can be recorded when ending the session and is not automatically a malware finding.

The report contains the public plan and its hash, build identity, per-case result summaries, incomplete/capture failures and the number not completed. It does not contain the locally held seed or private keys, and is not a replay bundle. Use Save evidence for a current transaction before advancing when the original returned bytes are needed.

Counts describe imported responses, not proven physical executions. The browser knows the disposable seed and cannot attest where a response came from. A matching session is not a firmware certificate or a measured security confidence level. The short wallet fingerprint is a comparison aid, not a unique identity or proof of safety.

Nothing is saved automatically. A new wallet or page reload discards the session. Back/Forward restoration may keep it in memory, but capture and advancement do not restart automatically. Keep one Lab version open and do not fund any test address.

How does this check for seed leakage?
Back to contents

Attacks such as Dark Skippy make a malicious signer hide seed information in the numbers used to create a signature, called nonces. They do not insert executable code into a transaction. An attacker who obtains the signed transaction can extract the hidden information. Broadcasting exposes it to observers of the mempool and blockchain, even if the signing device was offline.

This tool checks for deviations from supported deterministic signing methods. Using the same disposable seed and transaction, it calculates reference signatures and compares the returned signed transaction byte for byte. A match requires unchanged transaction data, valid signatures for every expected key, and an exact match with a supported reference.

The tool neither broadcasts transactions nor monitors the mempool. It does not inspect installed firmware. The published Dark Skippy example produces a mismatch, but other signature-based attacks can still pass. See the specific limits of this check.

Read the authors’ Dark Skippy explanation ↗

The published Dark Skippy example differs from the supported reference signatures. This is a signature comparison, not a search for an attacker’s secret watermark or an inspection of firmware. A matching test cannot rule out a conditional Dark Skippy variant, later seed leakage or attacks through other channels.

Spot checking is not anti-exfil protection. Keeping test keys disposable avoids exposing a funded wallet to the browser only while those keys are never funded or reused. Anti-exfil protocols add host contributions to the actual signing exchange. They are not inherently impossible over optical QR messages, but both applications must support the additional exchanges. This Lab does not implement that protocol, inspect firmware, or protect future real-wallet transactions.

Which numbers should match my signing device?
Back to contents

For a payment, compare the device’s send amount with To recipients, not Total inputs. Inputs also fund the fee and the money returned to the test wallet. For a self-transfer with no recipients, SeedSigner’s overview shows the amount returning to your wallet instead.

SeedSigner’s Transaction Math view shows input total, recipient total, fee and returned funds. It can display fees in sats even when the other values are in BTC. One BTC equals 100,000,000 sats; for example, 0.00003626 BTC is 3,626 sats. Use the BTC/Sats buttons to compare like units.

Wallet balance change is the negative of recipient payments plus the fee. It is not the amount a recipient receives. An estimated fee rate can differ slightly after signing because signature sizes vary; the absolute fee must match exactly.

Use a BIP84 path for an output returning to the test wallet. A pasted address is treated as a recipient because its ownership is not established by a path. If you edit or randomize the transaction, discard the old one on your signing device and scan the new QR. Do not continue with a test whose amounts or recipient addresses differ after comparing the same transaction in the same units.

What does an orange result mean?
Back to contents

Read the heading, not just the colour. Orange means the check needs attention; it is not a malware verdict.

“Signatures matched. File changes need review.” The transaction and signatures passed their checks, but other returned-file fields changed outside the recognized rules. Open Inspect file changes and preserve the result. The cause may be a legitimate unsupported transformation, unexpected data or a Lab defect. The saved bytes are needed to distinguish them; a device name alone is not an exemption.

“Could not complete the check.” The Lab could not establish a complete supported result. Read the specific error. A damaged transfer, wrong transaction, missing or invalid signature, or unsupported response must not be counted as a successful check.

A scan error before verification is a transfer failure, not a signature verdict. Save scan diagnostics when offered. No signature result exists until a complete response is checked.

Before advancing, choose Save result to preserve full evidence when available. An incomplete import may provide only a summary. Keep the original response and record the Lab version, device model, firmware, browser, opening mode and steps taken. Use only disposable-wallet data; never share a real seed. Evidence can contain untrusted signer data, so review it before sharing.

More green matches do not erase an orange finding. Do not weaken the signer’s safeguards or reset it based only on a colour. See what the evidence can establish.

What do the three result checks mean?
Back to contents

Transaction data: unchanged. The returned transaction preserves the prepared version, input outpoints and order, sequence values, output amounts, destination scripts and order, and locktime. This compares transaction data before signatures. It does not show what the firmware tried to do, inspect its code or establish that signatures contain no watermark.

Input signatures: N of N valid. Each input in this supported single-signature wallet requires one signature from its expected test-wallet key. Nine inputs therefore require nine signatures. The two outputs do not require two more signatures; every checked signature commits to all outputs through SIGHASH_ALL. Valid means mathematically valid for this test, not free of hidden information. The published Dark Skippy example has valid signatures too.

Reference comparison: matched. The final signed transaction bytes equal one supported deterministic reference calculated using this test seed and transaction. A nonce manipulation that changes those bytes away from every supported reference is flagged as a difference. The tool does not search for an attacker’s secret watermark, extract leaked seeds or prove that all possible watermarks and signature channels are absent. Read the limits, including choices between accepted reference methods.

Why does the browser ask for camera access again?
Back to contents

The Lab releases the camera after a response, on Stop, and when capture is interrupted. Starting another scan requests a new stream. The browser decides whether it remembers your permission or asks again; the page cannot promise or grant permanent access.

Check camera permissions for this specific Lab location in your browser. One-time permission, a new origin, a local-file opening mode or a private session may behave differently. Do not enable camera access for all websites. The camera never remains secretly active between tests. Repeated prompts during one uninterrupted scan need investigation; save diagnostics and record the browser and opening mode.

Why did a QR scan stop?
Back to contents

QR transfer and signature verification are separate. During camera capture, a small bounded number of malformed or checksum-invalid Bytewords frames may be rejected before admission. Their bytes are never used. The page reports the count and stops at 8 consecutive or 24 total rejected frames, or the existing scan deadline. Mixed transfers, conflicting valid frames, complete-message checksum failures and internal decoder errors stop immediately. A new scan always requires your action. Pasted/file submissions remain strict and are checked in full.

Use Save scan diagnostics to record the exact build, error code and rejection counts without the seed or raw QR data. No signature result exists until a complete response has passed the transport and transaction checks.

How do I use BBQr?
Back to contents

In step 2, choose BBQr under QR format. Only the QR transport changes, not the test PSBT. Outgoing BBQr uses compressed Base32 when smaller, otherwise Base32. BC-UR remains available.

In step 3, scan the signed response normally, import a text file, or paste every BBQr frame separated by whitespace. PSBT and signed-transaction BBQr responses accept Hex, Base32 and compressed encoding. Parts may arrive in any order. An incomplete, malformed or conflicting sequence is not a signature result. After a scan error, start a new scan explicitly.

BBQr has no whole-transfer identifier or checksum. Some interleaved sequences can share the same header. Scan one response at a time. The same transaction-binding and signature checks still apply before any result is accepted. A transport change does not certify signer firmware or add support for other signing algorithms.

Can I rely on the results?
Back to contents

This is an additional check of signing behavior, not an approval to trust firmware with savings. It can expose deviations such as the published Dark Skippy signatures when that behavior occurs in a tested transaction.

Rely on the specific finding, not a guarantee that firmware is safe. A match means all input signatures are valid for this test and the signed transaction equals a supported expected result. A mismatch means valid signatures differ; it can reflect malicious behavior or a legitimate unsupported signing method. Incomplete means the check could not establish those facts.

This reliability candidate adds bounded QR intake, explicit camera lifecycle handling, separate metadata assessment, immutable evidence and prepared-test caching. The mathematical signature checks retain the existing supported methods. The accompanying qualification report distinguishes automated checks, browser simulations, unavailable tests and hardware acceptance. Neither the tool, its dependencies nor your browser is guaranteed to be free of bugs. Physical camera and hardware acceptance remain pending.

Independent review is still needed. A public source repository and independently reproduced release artifacts have not yet been published for this edition. The automated checks are not a third-party security audit. Browser simulations do not establish secure-origin startup, file-opening behavior, physical-device scanning or camera compatibility.

If you report an issue, include the tool version, device and firmware version, the steps to reproduce it, and a saved test report if useful. Never include a real seed phrase or real-wallet signing data.

The browser knows the disposable seed and can produce the expected signatures itself. It cannot prove the imported data came from the named device. Reports record what was checked; device and firmware labels are your notes. Unexpected PSBT signing fields are rejected. Other returned PSBT fields are inventoried separately against a versioned change policy. An expected metadata result is not proof that every possible hidden-information channel is absent.

For regular use, keep the tool version and reports, compare the same transaction on the device, and investigate any mismatch or incomplete result. Testing is an additional check alongside firmware authenticity verification and device safeguards, not a replacement for them.

How does this compare with the original tool?
Back to contents

The underlying detection method and three reference signing algorithms come from exfil-tester v0.1.4. Both compare signed transaction bytes with deterministic expectations. Neither can certify firmware as safe.

This edition adds stricter transaction and signature validation, rejection of contradictory PSBT signing fields, separate metadata assessment, clearer incomplete results, protected completed tests, replayable public evidence and bounded QR/camera handling. It retains input/output customization and uses generated disposable seeds. The original also offers manual seed entry and a demonstration loader. This edition opens its recorded-attack example separately from the wallet workflow, so it cannot replace an active test.

These are improvements to input handling, result interpretation and workflow reliability. They do not establish a higher detection rate against arbitrary malicious firmware.

Why run several tests with the same seed?
Back to contents

As a practical routine, try 20 randomized transactions with the same disposable seed. Keeping it loaded makes repeats simpler. Each signed transaction is checked separately; 20 is a suggestion, not a validated security threshold.

New transaction changes inputs, outputs and locktime. Customize gives you direct control. Malicious firmware may trigger only for particular amounts, input patterns, wallets or later transactions, and may recognize these invented inputs. Even 20 matching tests cannot prove the device is safe.

The tracker counts distinct completed transactions with this seed, with matches and differences shown separately. Generated-but-unchecked transactions, incomplete imports and the demonstration do not count. Rechecking the same transaction does not add progress; if it ever differs, that difference remains in the session tally. More matches do not cancel a difference. There is no safety certificate or confidence percentage at 20, and you can keep testing. It counts supplied transactions, not proven hardware executions.

Test numbers start at 001 for each new seed. New transaction advances the number while keeping that seed. It counts generated transactions, not successful checks. Completed matches and mismatches are read only; incomplete imports can be corrected. The separate tracker resets with a new seed or page reload. It stays in this tab’s memory, including a restored Back/Forward page. Save report includes its current tally and transaction IDs without the seed. Investigate differences or incomplete checks before continuing. Read why conditional behavior matters.

Which scenarios are tested, and how random are they?
Back to contents

New transaction chooses randomly among the least-completed scenario types for this seed. Completing each generated test therefore spreads checks across all six types. Skipping a test does not add coverage. Editing its inputs, outputs or locktime labels it Custom and does not count toward a generated type. Counts measure examples checked, not exhaustive coverage or firmware confidence.

Payment bands refer to the total sent to recipients, excluding change and fees. Payment profiles use 1–4 inputs; multiple-recipient profiles use 1–6. Both vary whether change is present. Input and output order is shuffled. Recipient amounts mix individual sats with rounded hundreds and thousands. Change and consolidation use wallet paths; recipient addresses are random native SegWit addresses.

Ordinary scenarios use locktime 0 and sequence 0xfffffffd or 0xffffffff. Fees use a conservative P2WPKH size estimate and a simulated rate: 1–5 sat/vB for small payments and consolidation, 1–15 for medium, and 1–25 for large and multiple-recipient payments. These are test settings, not live network fee estimates. The review shows the actual absolute fee and an estimated signed fee rate.

Boundary cases choose payment thresholds of 600 sats, 1,000 sats, 100,000 ±1, 10,000,000 ±1, 100,000,000 ±1 or 1,000,000,000 sats, raised when needed to keep each input/output at least 600 sats. They probe locktime 0, 499,999,999, 500,000,000 or 4,294,967,295 with sequence 0xfffffffd, 0xfffffffe or 0xffffffff, and simulated rates of 1, 50 or 100 sat/vB. These cases are deliberately unusual. A device may refuse them; that alone is not a malware finding. In Customize, choose another scenario to continue; the refused type remains untested. Do not weaken its protections.

All generation uses cryptographic randomness and unbiased integer rejection sampling; amounts and scenario types intentionally follow the stated sampling policy, not a uniform distribution over every possible transaction. Every input has an invented 32-byte transaction ID, an output index 0–5 (0–100 for boundary cases), and a receive/change index 0–500 in BIP84 account 0. Nothing is fetched from the blockchain. A 12-word seed uses 128 bits of entropy; a 24-word seed uses 256 bits.

The independent shuffles in Customize retain their broader original controls: input shuffle makes 2–10 inputs of 2,000–1,000,000,000 sats with output indices 0–100 and sequence 0xfffffffd. Output shuffle creates a payment plus change with a fee of 141–5,000 sats within budget. Locktime shuffle selects 900,000–2,000,000. You can manually edit up to 20 inputs and outputs. Shuffling inputs leaves outputs unchanged; shuffle outputs to rebalance if necessary.

These profiles mix plausible payment shapes with deliberate edge cases. They are not calibrated to a measured distribution of real users’ payments. There is no custom test flag in the PSBT, and downloads use invented descriptive filenames, such as invoice-4837.psbt. A label stays the same when downloading the same PSBT again; it is not embedded in the transaction or QR. An offline signer without blockchain history cannot establish that an input is invented just by looking at its random transaction ID. However, recognizable payload patterns, wallet history or other clues can suggest testing. There is no percentage of realism or guarantee that firmware mistakes these for real funds. Better variety does not establish a measured increase in detection probability. Never fund this browser-exposed wallet.

What can a match tell me, and what can it miss?
Back to contents

A match confirms a supported reference result for this transaction. It cannot rule out every way of hiding information, even in signatures. A malicious signer can behave honestly for a test and leak seed information later. Twenty randomized tests are a suggested routine, not a proven safety threshold.

Compatibility mode accepts plain RFC 6979, Bitcoin Core low-R grinding and embit DER-length grinding. A fixed policy can be selected before import to require one method. No device profile is automatically selected or certified, and methods can coincide for the same transaction. Those methods can produce different valid reference signatures for the same transaction. The checker does not establish why the signer chose one: choosing between accepted results could itself carry information. This is a limitation inferred from the comparison policy, not a finding that a particular device does this. A match therefore means a match to one accepted reference, not proof that every possible signature channel is free of leakage.

Taproot/Schnorr, multisig, non-BIP84 input scripts, BIP39 passphrases, randomized nonces and anti-exfil protocols are outside this version's supported test flow. Device names are report labels, not compatibility certifications. This page does not inspect firmware or attest where imported signatures came from. Pasting the reference signatures can produce a match without testing any device. PSBT metadata changes are reported separately; this does not prove the absence of covert channels, including choices between accepted results or information hidden in valid data.

Repeated matches do not establish that firmware is honest. A signer may recognize a test or behave differently for another amount, wallet, input, block height or later transaction. This tool also does not audit firmware, seed generation, supply chains or the browser running it. This release does not register a browser-agent status tool. That does not stop a browser or extension with access to this page from observing its contents. Field order can change legitimately or carry information to a recipient of the PSBT; order observations do not certify the absence of hidden channels.

If a device refuses the fake transaction, stop there. Do not weaken device protections, overwrite a real wallet or fund this disposable wallet to make the test work.

The reference methods can genuinely differ. Bitcoin Core-style grinding requires a low r value; the embit variant stops at a DER signature length of at most 70 bytes, which can include a higher r when s is short. Neither a shared result nor a different accepted reference identifies a device or proves malicious behavior. Calling one method a standard does not remove the information channel created by accepting several methods. Fixed-policy checks retain their existing meaning and must be selected before import.

Taproot remains outside this release. BIP 340 signatures can be reproducible under a specifically known auxiliary-input policy. A different valid signature does not prove that a device used fresh randomness, and a matching signature does not prove a safe nonce source. Do not disable signer randomness or other protections to force a match. Taproot would require separate transaction, derivation, sighash, PSBT and physical-device qualification, not just another reference label.

Why did my signer return a smaller file?
Back to contents

A reduced signing response is not automatically an error. Some signers remove supporting PSBT fields to return a smaller response. A narrowly recognized signature-only envelope, including an exact SIGHASH_ALL field when present, is described neutrally only alongside the existing transaction and signature checks. Selective omissions, changed fields and unknown additions are not silently allowed. They receive a separate review finding. No device-name label exempts a response.

A match with unresolved file changes is amber: Signatures matched. File changes need review. Expected cleanup is recorded in evidence, not treated as proof against every hidden channel. Save current evidence before advancing. These rules cannot retrospectively diagnose a screenshot without the actual returned bytes.

What is checked in returned-file metadata and evidence?
Back to contents

The PSBT envelope is the set of fields around its signatures. Every parsed key/value field is inventoried. Evidence also records its zero-based position before and after signing. Relative-order changes among retained keys are reported separately; normal signing additions are not automatically called reordering. Unchanged fields and a small, versioned set of normal signing/finalization changes are distinguished from unexpected additions, removals or changes. Unknown or proprietary fields are not automatically malicious. Raw signed transactions have no PSBT metadata to compare.

Save report and Save evidence use the same frozen result. Evidence also includes the exact returned bytes, public prepared PSBT, input amounts, keys, signature digests and reference results. It does not add the locally held seed or private keys. Untrusted returned data can itself contain hidden information; use disposable wallets and review evidence before sharing.

The public replay tool verifies transaction binding, signatures and consistency with saved references. It also independently reproduces psbt-envelope-v3 metadata findings and verifies session-evidence attachments. Unsupported policies are rejected. It cannot derive a secret-key nonce, authenticate references, prove hardware origin or certify firmware. Optional retention in Session keeps public evidence in this tab only; missing responses remain explicit. Nothing is saved to disk automatically.
